# PriceChecker.Web frontend

React 19 + TypeScript SPA. State via Redux Toolkit + redux-saga. UI with PrimeReact. Bundled by Vite. Tested with Vitest. Live scan updates arrive over SignalR. Shared building blocks come from the private `@hwndmaster/atom-*` packages.

**Package manager is `pnpm`** (pinned via the `packageManager` field in `PriceChecker.Web/package.json` — currently `pnpm@11.9.0`; CI reads that field, so bump it there and nothing drifts). Never use `npm` or `yarn`. All commands run from `PriceChecker.Web/`.

## Commands

| Task                  | Command (cwd = `PriceChecker.Web`)          |
| --------------------- | ------------------------------------------- |
| Install deps          | `pnpm install`                              |
| Dev server            | `pnpm start` (port 5081, opens browser)     |
| Dev server (Aspire)   | `pnpm start:aspire`                         |
| Build                 | `pnpm build` (output in `build/`)           |
| Lint                  | `pnpm lint` (eslint, cached)                |
| Test (watch/run)      | `pnpm test`                                 |
| Test + coverage       | `pnpm test:coverage` → `coverage/lcov.info` |
| Regenerate API client | `pnpm nswag` (after API contract changes)   |

After any change, run **`pnpm lint`** and **`pnpm test`** before considering it done. The build also typechecks. `pnpm nswag` needs the API running (`dotnet run --project PriceChecker.WebApi`, port 5080).

## Project layout (`src/`)

- `api/` — generated HTTP client. `api.generated.ts` is **generated by NSwag from the WebApi** (config in `nswag/webapi.nswag`) — never hand-edit it; run `pnpm nswag`. `apiAxios.ts` wires the singleton axios client; `setup.ts` configures it; `converters/` convert between API DTOs and app models (one per domain: agents, products, settings), `fieldMapping/` adapts field names from the backend (C#) to app DTO field names when processing validation errors from the server.
- `store/` — one folder per domain slice (`agents`, `products`, `scans`, `settings`). `setup.ts` builds the store via `createAppStore` from `@hwndmaster/atom-react-redux` with **redux-persist** (`persistKey: "root"`, `persistBlacklist: ["common", "scans"]` — scan progress is transient) — bump `persistVersion` when changing the shape of persisted state. `setupSagas.ts` registers sagas; `appState.ts` is the root state; `utils.ts` holds `typedSelect`; `testUtils/sagas.ts` exposes `fakeAxios`. `index.ts` re-exports each slice as a namespace (`store.Products.Actions`, `store.Scans.Selectors`, …) — UI code imports `* as store from "@/store"` and goes through those.
- `components/` — reusable UI (`agentEdit`, `productEdit`, `scanProgress`, `layout`). Forms use `react-hook-form` + zod schemas (`schemas/*.ts`) via `@hookform/resolvers`.
- `pages/` — route-level screens (`products`, `agents`, `settings`, `error`, `notFound`). Routing via **`react-router` v8** in `RootComponent.tsx` (`createBrowserRouter` from `react-router`, `RouterProvider` from `react-router/dom` — not `react-router-dom`); paths come from `shared/routes.ts`.
- `models/` — app-side types per domain + `types.ts` (Guid reference-type factories) + `enums.ts`.
- `styles/` — global SCSS (`main.scss`, `_variables.scss`, `_mixins.scss`, `datatable.scss`, `forms.scss`, `photo.scss`); variables/mixins are auto-injected into every SCSS module by `vite.config.ts`.
- `telemetry/` — OpenTelemetry setup (`setupOpenTelemetry.ts`), called once from `index.tsx`.
- `primereact.ts` — barrel re-exporting every PrimeReact component in use; import PrimeReact components from here, not from `primereact/*` directly.
- `schemas/` (zod), `shared/` (constants, formatters, `loadingTargets.ts`, routes, `scanStatus.ts`), `utils/` (incl. `utils/tests/testModels.ts`).

## Guid entity references

Backend ids are Guids, not ints. `models/types.ts` declares them via `EntityGuidId<"Agent">` and `createGuidRefConverter` from `@hwndmaster/atom-web-core` (`agentRef`, `productRef`, `productSourceRef`, `productPriceRef`). Use the factories (`productRef(guid)`, `productRef.default()` for "new entity") instead of raw strings, both in app code and in tests.

## Store slice pattern (Redux Toolkit + saga)

Each slice folder has a fixed file set — follow it exactly when adding a slice:

- `state.ts` — the slice's state interface.
- `actions.ts` — **public** actions, the only ones other modules dispatch.
- `actionsInternal.ts` — **internal** actions dispatched only by sagas/reducers within the slice.
- `reducers.ts` — `createReducer` over `actionsInternal` (a reducer may also react to another slice's public actions — `products/reducers.ts` reacts to `scans` actions).
- `sagas.ts` — `function*` sagas using `redux-saga/effects` and `callApi` from `@hwndmaster/atom-react-redux`; call the API via `apiClient().<client>.<method>()`, use converters from `/api/converters` when calling `fetch`/`fetchArray`.
- `selectors.ts` — selectors over the slice state (use `typedSelect` from `store/utils.ts` in sagas).
- `messages.ts` — the slice's non-store API surface. `scans/messages.ts` owns the SignalR hub connection (`startScanHubConnection`, `${ApiUrl}/hubs/scan`) and dispatches store actions from hub callbacks; `agents/messages.ts` exposes a plain fetch for static data. Only present where needed (`products` and `settings` have none).
- `index.ts` — re-exports `* as Actions` and `type * as State`.
- `*.test.ts` — reducer and saga tests colocated.

## Action creators

* Use `createAction` from `@reduxjs/toolkit` for simple scenarios.
* Use `createActionWithMeta` from `@hwndmaster/atom-react-redux` when the caller must handle the result (error toast on rejection, redirect on success).
* Use `createActionWithMetaValidatable` when the saga result may contain a validation result (form submissions).

## Wrappers in sagas

* Use `withLoading` to block a part of the UI, where the part is defined via `LoadingTargets` (`shared/loadingTargets.ts`; pass a third argument to scope the loader to a single entity, as `fetchPricesSaga` does).
* Use `withCallback` to handle actions created using `createActionWithMeta`.
* Use `withValidatableCallback` to handle actions created using `createActionWithMetaValidatable`, passing the slice's `mapValidationField`.

## Architectural boundaries (enforced by ESLint `import-x/no-restricted-paths`)

These are hard rules — violating them fails lint:

- The `api/` folder may **only** be imported from `store/`.
- Within a slice, only `sagas.ts`, `messages.ts`, and `apiRequest.ts` may import from `api/`.
- `actionsInternal.ts` may only be imported within `store/`.
- `sagas.ts` may only be imported within `store/`.

So: UI (`components/`, `pages/`) dispatches **public** actions and reads state via selectors/hooks; it never touches `api/` or `actionsInternal` directly.

## Testing conventions

- Vitest with `globals: true` (no need to import `describe`/`it`/`expect`), `jsdom` environment, `setupTests.ts` setup file. The `@hwndmaster/atom-*` packages are inlined via `server.deps.inline` in `vitest.config.ts` — add new ones there.
- Tests are colocated as `*.test.ts(x)`.
- Sagas: use `SagaRunner` from `@hwndmaster/atom-testing-utils`; mock HTTP with `fakeAxios` from `@/store/testUtils/sagas` (`fakeAxios.setupGet(api.AgentsClient, "agentsAll").reply(200, [dto])`). Reset `fakeAxios`, `sagaRunner`, and `vi.clearAllMocks()` in `beforeEach`. Assert dispatches with `sagaRunner.findDispatchedAction(...)`, including the `Common.Actions.showLoader`/`hideLoader` pair.
- Reducers: build state through a local `createState(overrides?)` helper and assert on the returned state.
- Use the `@/` path alias for `src/` imports.
- Follow the **Arrange / Act / Assert** comment structure.
- **ALWAYS** select screen elements by their `data-test_id` attributes in tests. If an element is missing one, add it to the component. Format: `ComponentName__Element_Description`, e.g. `ProductEdit__Save_Button`. Avoid selecting by content text.
- Use the model factories from `utils/tests/testModels.ts` (`createAgent`, `createProduct`, `createProductOverview`, `createProductPrice`, `createScanProgress`) with `Partial<T>` overrides instead of hand-building objects; extend that file when a new domain model needs one.
- When testing a specific function (reducer/action/etc.), name the test `functionName: description of the test case`.
- Do NOT write exhaustive test suites — cover rendering, main logic, standard business scenarios, and the most likely edge cases.

## Conventions

- Indentation: 4 spaces; double-quoted strings (matches existing files and stylistic config).
- Prefer PrimeReact components (via the `src/primereact.ts` barrel) and the `@hwndmaster/atom-react-*` helpers over hand-rolling.
- Validation schemas use `zod` (v4) under `schemas/`, wired to forms via `react-hook-form` + `@hookform/resolvers`.
- Avoid conversion like `as unknown as Type` or `as unknown as never` unless absolutely necessary — restructure types instead.
- Import order in a React component file:
  1. React and related libraries
  2. Third-party libraries
  3. `@hwndmaster/atom-*` packages
  4. Application-wide imports, with the following order:
     - Store imports (e.g., `import * as store from "@/store";`)
     - API imports (e.g., `import * as api from "@/api/api.generated";`)
     - Model imports (e.g., `import ProductOverview from "@/models/productOverview";`)
     - Utility imports (e.g., `import { formatPrice } from "@/shared/formatters";`)
     - Component imports (e.g., `import ProductEdit from "@/components/productEdit/productEdit";`)
  5. Components from upper folder (e.g., `import AnotherComponent from "../anotherComponent";`)
  6. Local imports (e.g., `import AnotherComponent from "./anotherComponent";`)
  7. Styles (e.g., `import "./myComponent.module.scss";`)

## CSS Styling

- Always use SCSS Modules or `main.scss`; stack styles in layers (component / feature / global).
- Use camelCase for CSS class names; access them as `styles.myClassName` (no bracket notation).

## Naming conventions

- PascalCase for type names and constants (`const MaxUsers = 100;`), camelCase for variables and functions — per the `@typescript-eslint/naming-convention` rules shipped in `@hwndmaster/atom-eslint-stylistic` (pulled in by `eslint.config.js`).

## Atom-web packages

- Packages under the `@hwndmaster` scope are called atom-web packages.
- If you need to change any atom-web package, ask first, then make the change. Afterwards ask for the new versions to be published and continue; if publishing is deferred, assume the published versions will contain your changes and proceed without waiting.
